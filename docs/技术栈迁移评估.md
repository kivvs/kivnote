# KivNote 技术栈迁移评估：Electron → Tauri

> 状态：**评估稿（已定方向，待执行）**。
> 决策：用 Tauri（Rust + 系统 WebView2）替换 Electron，目标"大幅降低运行内存"。
> 关联文档：`../KIVNOTE_SUMMARY.md`（项目概述）、`docs/PLUGIN_ARCHITECTURE.md`（其中已明确"降到 100MB 以下只能换 Tauri/WebView2"）。
> 日期：2026-10-22。

---

## 1. 决策背景与目标

### 实测基线（来自 KIVNOTE_SUMMARY.md）
| 场景 | 内存 |
|------|------|
| 空窗口 | ~345MB（渲染 ~185 + 主 ~107 + 实用 ~53） |
| 2 万行 CSV | ~425MB |

关键结论：**渲染进程 185MB 是 Chromium 固定开销**，与功能代码基本无关（空 HTML 页也是这个量级）。`PLUGIN_ARCHITECTURE.md` 已承认：插件化只能优化"安装体积 + 增长曲线"，**动不了单窗口基线**。

### 本次目标
- 单窗口基线内存从 ~345MB 降到 **~80–150MB**（降 50%+）。
- 尽量**复用现有前端资产**（`renderer/index.html` + `style.css` + 全部 UI 逻辑）。
- 保留全部已交付能力：虚拟滚动、行号高亮、PDF 文本层/缩略图/查找/旋转导出、xlsx 保格式、编码切换、LibreOffice 转换。

---

## 2. 为什么是 Tauri（而非继续 Electron / 其他）

| 维度 | Electron（现状） | Tauri（目标） | Neutralino | 完全原生(Qt/WPF) |
|------|----------------|--------------|-----------|----------------|
| 渲染内核 | 自带 Chromium ~150MB | 系统 WebView2（共享） | 系统 WebView2 | 原生控件 |
| 空窗内存 | ~345MB | ~80–150MB | ~60–120MB | ~30–80MB |
| 前端复用 | — | ✅ 原样跑 HTML/JS | ✅ 原样跑 | ❌ 整体重写 |
| 后端语言 | Node/JS | **Rust** | JS | C++/C#/Dart |
| 二进制体积 |  bundled Chromium | 极小（无内核） | 小 | 小 |

选 Tauri 的理由：**WebView2 复用系统 Edge 内核，直接消除 185MB Chromium 固定开销；前端 HTML/CSS/JS 资产几乎零成本迁移；安全模型比 Electron 的 `contextIsolation` 更彻底（前端无 Node、无 `require`）。**

> ⚠️ 个人偏好提示（见用户记忆"能看懂优先"）：Rust 学习曲线偏陡、写法不够"直白"。若重写后端时觉得 Rust 成本过高，可**无缝回退到 Wails（Go 后端 + 同样 WebView2）**，前端资产完全通用。本文档以 Tauri 为主线，Wails 作为备选在 §11 说明。

---

## 3. 架构映射总览

```
Electron 三层                         →   Tauri 两层
─────────────────────────────────────────────────────────────
main.js（主进程 / Node）              →   src-tauri/（Rust）
  - 文件分类、解码、hex 读写              - 同样的纯逻辑，用 Rust 重写
  - xlsx/docx/pptx 改值                 - 命令(commands)经 invoke 暴露给前端
  - PDF 文本提取(pdfjs-dist)            - 调用 LibreOffice 用 std::process
  - LibreOffice 转换、菜单、最近文件     - 窗口/菜单/最近文件用 Tauri API
preload.js（contextBridge→native）   →   @tauri-apps/api（前端直接 import）
  - window.native.xxx                  - import { invoke } from '@tauri-apps/api/tauri'
renderer/index.html（UI 逻辑）        →   webview 内原样运行
  - 文本/表格/PDF/hex/图片/office        - 仅替换 native.xxx 调用为 @tauri-apps/api
```

**好消息**：`renderer/index.html` + `style.css` + 所有 UI 逻辑（虚拟滚动、行号高亮、PDF 文本层、缩略图、查找、hex 编辑器）**可直接放进 Tauri 的 webview 跑**，无需重写。改动面集中在：
1. 后端 `main.js`（1133 行）整体用 Rust 重写；
2. 前端把 `window.native.xxx`（由 preload 桥接）换成 `@tauri-apps/api` 对应调用。

## 4. 后端模块逐条重写映射（基于 main.js 实际职责）

| 现有 main.js 职责 | Tauri/Rust 实现 | 关键 crate / 注意点 |
|------------------|----------------|---------------------|
| 文件类型分类（魔数 sniff + 扩展名 `TEXT_EXT` 等） | Rust 函数：读头部字节判类型 + 扩展名匹配 | 纯逻辑，直译即可 |
| 文本解码（UTF-8/GBK 自动识别，`iconv-lite`） | Rust 解码 | `encoding_rs`（GB18030 覆盖 GBK，比 iconv 更全） |
| 二进制/hex 读写（`file:chunk` / `file:writeBytes` 按偏移打补丁） | `std::fs::OpenOptions` + `seek` + `write` | 字节级随机写，Rust 处理更直接 |
| xlsx 就地改值（`patchCellInXml` / `xmlEscape` / `isNumericLike` + 压缩炸弹防护） | 解压 zip → 改 sheet/sharedStrings XML → 重压 | `zip` crate + `quick-xml`/`roxmltree`；**保留"先算未压缩总大小再解"的炸弹防护** |
| docx/pptx parts 解析（`doc:parts` / `ppt:parts` / `ppt:renderNative`） | 同上 zip + XML 解析 | 逻辑平移 |
| PDF 文本提取（主进程 `pdfjs-dist/legacy`） | **改在前端用现有 PDF.js**（renderer 已集成），Rust 侧可不负责 | 减少后端复杂度；如需后端提取可用 `pdfium` crate 备选 |
| LibreOffice 转换（`lo:convert`，外部进程） | `std::process::Command` 调 `loffice/soffice` | 外部引擎不变，261MB 解压开销与框架无关 |
| 最近打开文件、窗口生命周期、dirty 标记 | Tauri 自带 `recent`/`window` API + Rust 状态 | 比 Electron 手动管理更省心 |
| 编码保存（`file:save` 接收 `saveEnc`） | `invoke('save_file', {path, content, enc})` → Rust 按 `encoding_rs` 写 | 保留状态栏编码切换 |
| CLI 参数（`--open` / `--shot` 等） | Tauri 支持 `await app.getArgs()` / 自定义协议 | 截图/测试参数需重新接 |

**压缩炸弹防护必须保留**：现有 xlsx/docx/pptx 解压前会校验总未压缩大小，这是安全关键逻辑，重写时一字不漏地平移。

## 5. 前端（renderer）改造清单

基本复用，只需做"接口替换"和"去 Electron 化"：

1. **移除 `preload.js` 依赖**：前端不再通过 `window.native` 访问系统能力。
2. **替换 native API 调用**（机械替换，量大但简单）：
   ```js
   // 旧（Electron + preload）
   const buf = await window.native.readAll(path);
   await window.native.save(path, content, enc);
   // 新（Tauri）
   import { invoke } from '@tauri-apps/api/tauri';
   import { readFile, writeFile } from '@tauri-apps/api/fs'; // 或走 invoke
   const buf = await invoke('read_all', { path });
   await invoke('save_file', { path, content, enc });
   ```
3. **移除 `require('electron')` / `ipcRenderer`**：前端代码中不应再有 Node/Electron 引用（WebView2 环境下会报错）。
4. **PDF.js / pdf-lib / SheetJS 继续在前端跑**：它们是纯 JS，无需改动；`withPdfLib` / `parsePageRange` / `bytesToB64` 等逻辑全部保留。
5. **验证 PDF.js 在 WebView2 的渲染**：这是唯一的"未知项"，需在 PoC 阶段实测文本层、缩略图、查找是否正常（Chromium 与 WebView2 的 JS 引擎都是 V8 系，预期兼容，但须实跑确认）。

## 6. 依赖库迁移对照

| 现有依赖 | 位置 | 迁移策略 |
|---------|------|---------|
| `pdfjs-dist` | 主进程提取文本 | 改前端用 renderer 已有 PDF.js（不变） |
| `pdf-lib` | 前端按需加载（旋转/导出页） | 保留（纯 JS） |
| `xlsx` (SheetJS) | 前端保格式写入 | 保留（纯 JS） |
| `iconv-lite` | 主进程 GBK 解码 | Rust 侧用 `encoding_rs` 替代 |
| `adm-zip` | 主进程 zip 读写 | Rust 侧用 `zip` crate 替代 |
| `electron` / `electron-builder` | 运行时/打包 | 替换为 `tauri` + `tauri-build`（NSIS/MSI） |

## 7. 风险与坑

1. **WebView2 ≠ Chromium 完全一致**：CSS 特性、某些 Web API 行为可能有细微差异；`renderer/index.html` 的 126KB 逻辑需整体在 WebView2 跑一遍回归（重点：PDF.js、虚拟滚动、拖拽）。
2. **Rust 后端重写成本 + 学习曲线**：`main.js` 1133 行逻辑不复杂但量不小；若团队/个人不熟悉 Rust，进度会慢。→ 备选 Wails(Go)。
3. **WebView2 运行时分发**：Windows 10/11 大多已内置；打包时可勾选"内置 WebView2 引导器"（Tauri 支持），避免用户缺运行时。
4. **文件关联 / 单实例 / 托盘**：Electron 的 `fileAssociations`、单例锁、托盘需改用 Tauri 插件（`tauri-plugin-*`）或 Rust 实现。
5. **LibreOffice 261MB 解压开销不变**：这是 Office 引擎本身，与框架无关，迁移后仍在（属预期）。
6. **打包镜像**：Electron 打包需 `ELECTRON_MIRROR` 等镜像；Tauri 一般无需，但首次拉取 Rust 依赖/WebView2 引导器要注意本机代理（见 KIVNOTE_SUMMARY.md 的代理坑）。

## 8. 分阶段迁移计划

- **Phase 0 — PoC（验证内存与 PDF.js）**
  搭最小 Tauri 壳，把 `renderer/index.html` 原样塞进 webview，打通"打开文件 → `invoke` 读内容 → 渲染"。**第一步目标：实测空窗内存**，确认落在 ~80–150MB，并确认 PDF.js 在 WebView2 正常。
- **Phase 1 — 后端核心（文件读/解码/保存/hex）**
  Rust 重写分类、UTF-8/GBK 解码（`encoding_rs`）、hex 随机写、最近文件。
- **Phase 2 — 表格/文档改值 + 压缩炸弹防护**
  `zip` + `quick-xml` 重写 xlsx/docx/pptx 就地改值，保留炸弹防护。
- **Phase 3 — PDF 文本提取迁移**
  确认前端 PDF.js 路径，必要时 Rust `pdfium` 备选。
- **Phase 4 — LibreOffice 转换**
  `std::process::Command` 调 `loffice`，复用现有参数与进度逻辑。
- **Phase 5 — 菜单/编码切换/单实例/文件关联**
  Tauri API + 插件补齐 Electron 原有行为。
- **Phase 6 — 打包发布**
  `tauri-build` 出 NSIS/MSI/Portable；**保留"逐个 `gh release upload`"的发版流程**（一次性传多文件会卡，见 KIVNOTE_SUMMARY.md）。

## 9. 验证与测试策略

- **原 12 个单元测试的去向**：
  - 纯逻辑类（`isNumericLike` / `xmlEscape` / `patchCellInXml` / `colName` / `parsePageRange` / `toCSV`）→ 用 Rust `#[cfg(test)]` 重写等价断言（这些是内存/正确性关键，必须留）。
  - 前端逻辑类 → 保留为 webview 内 JS 测试或 Puppeteer-style 冒烟。
- **回归清单**：PDF 文本层 / 缩略图 / 查找 / 旋转导出、表格虚拟滚动 5 万行、hex 编辑、GBK 文件打开、xlsx 保格式、LibreOffice docx→pdf。
- **内存验收**：空窗 ≤150MB、2 万行 CSV ≤200MB（对比原 345/425MB，降幅 ≥50% 即达标）。

---

## 10. 结论

Tauri 是本项目在"大幅降内存"目标下的**最优解**：直接消除 Chromium 固定开销、前端资产近乎零成本复用、安全模型更优。主要成本是 **Rust 后端重写**（约 `main.js` 量级的逻辑）+ **WebView2 兼容性回归**。Phase 0 的 PoC 应先确认内存数字与 PDF.js 兼容性，再全面铺开。

若 Rust 成为瓶颈，立即切换 **Wails(Go)** 后端——前端 `renderer/` 资产完全不变，仅后端语言替换，风险可控。
